# xenOS "AI-First" — Networking → Chat Box → Agent (staged)

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Point xenOS at an external LLM provider (OpenCode Go, ChatGPT/OpenAI, or any
OpenAI-compatible API) and give it a working **chat box** — configured by exactly three
fields (**model name, endpoint, token**). Staging enforced by the user:
**Stage 0 = networking**, **Stage 1 = a simple chat box** (the first product), **Stages
2–3 = agent territory later.** Nothing is embedded in-kernel; the OS is a client.

**Architecture:** An `ai` subsystem with three layers, carried by a from-scratch network
stack:
1. **Provider config** — `AI.CFG` on FAT: `model=`, `endpoint=`, `token=`. Loaded/validated
   at boot; masked display.
2. **Provider-agnostic client** — builds the OpenAI-compatible `chat/completions` request
   (`{ "model", "messages":[{"role":"user","content":prompt}] }`, `Authorization:
   Bearer <token>`, `Content-Type: application/json`) and parses
   `choices[0].message.content`.
3. **Chat box UI** — a WM app window (reuse `xk_wm.c3`/`xk_apps.c3`) with a scrollback
   of user/model turns, a text input line, and a send path through the client.

**Tech Stack:** C3 (freestanding, `--x86cpu=baseline --x86vec=none`), NASM, GNU ld, QEMU
(qemu64, TCG). No libc in-kernel. Reuse `xk_fat.c3`, `int 0x80` gate, `xk_umode.c3`,
`xk_shell.c3`, VESA WM. **No NIC/TCP/IP/TLS exists yet — Stage 0 builds all of it from
scratch.**

## Stage 0 — Networking (highest priority, the long pole)

xenOS has **no NIC driver, no ARP/IP/IPv4 stack, no TCP, no HTTP client, no TLS.** This
stage is a from-scratch networking project and must come first because nothing above it can
run without bytes on the wire.

### Task 0.0: reachability spike (de-risk before building)
**Objective:** Prove a guest can receive bytes over the host bridge before investing in
the full stack. Use QEMU `-netdev user` + `-device e1000` (simple DMA NIC; virtio-net is
the fallback) and a `-net user,hostfwd` port-forward to a plaintext host mock.
**Files:** `tools/ai_mock.c3` (freestanding host C3 serving a canned completion over raw
TCP); QEMU launch flags in `run.sh`.
**Verification:** Guest connects and prints the canned bytes. If QEMU's DMA-to-guest proves
flaky (as with AHCI), this is where we learn it cheaply.

### Task 0.1: e1000 NIC driver (`xk_net.c3`)
**Objective:** From-scratch DMA ring driver: allocate TX/RX ring buffers, program the NIC
registers/descriptors (compare the DMA pattern to the existing AHCI work, reusing its
lessons), receive path into a kernel ring.
**Files:** Create `kernel/src/xk_net.c3`.
**Verification:** With the mock running, the RX ring receives the mock's packet bytes.

### Task 0.2: ARP + IP + TCP client (`xk_ip.c3`, `xk_tcp.c3`)
**Objective:** ARP resolution for the gateway/host, a minimal IPv4/IP frame path, and a
small TCP client (SYN/SYN-ACK/ACK, SEQ/ACK accounting, a few retransmits, teardown).
Connect toward the host-forwarded service.
**Files:** Create `kernel/src/xk_ip.c3`, `kernel/src/xk_tcp.c3`.
**Verification:** Guest opens a TCP connection to the host mock and round-trips a request.

### Task 0.3: HTTP/1.1 client filling the transport seam (`xk_http.c3`)
**Objective:** Request/response HTTP/1.1 (POST, `Content-Length`, read body). Plugged into
the `AiTransport`'s function-pointer seam so the client layer is transport-independent.
**Files:** Create `kernel/src/xk_http.c3`; adapt `xk_ai_client.c3`.
**Verification:** Query the mock over HTTP and fully receive a published completion.

### Task 0.4: TLS decision point
**Objective:** Real providers are HTTPS-only. Decide and record in `docs/ai-first.md`:
(a) later minimal TLS 1.2 + AES-GCM (large, no borrowed code), or (b) for now the chat box
talks to a local host TLS-terminating proxy / plaintext mock over the bridge — the
shippable demo. Recommend (b) now, (a) tracked as a later milestone.
**Files:** `docs/ai-first.md`.
Commit: `feat(net): e1000 + ARP/IP/TCP + HTTP over host bridge (mock provider)`.

## Stage 1 — Simple chat box (first product)

Goal: the GUI chat window the user can actually type into. Config is a precondition here
(model/endpoint/token are what the chat box sends), so config lands at the start of this
stage.

### Task 1.1: provider config `AI.CFG` (model / endpoint / token)
**Files:** Create `kernel/src/xk_ai_cfg.c3`; modify `tools/mkfat.c3` (seed a placeholder
`AI.CFG`, never a real token), `kernel/src/xk_main.c3` (load at boot).
**Verification:** `aicfg show` prints model/endpoint and masked token; parse errors reported.

### Task 1.2: provider-agnostic client (request builder + response parser)
**Files:** Create `kernel/src/xk_ai_client.c3`; `tools/ai_req_test.c3` (host C3 harness).
**Verification:** harness asserts the exact JSON request bytes and the extracted
`choices[0].message.content` byte-for-byte — before any network risk.

### Task 1.3: chat box window (WM app)
**Objective:** A titled window with scrollback (user turns + model turns), a text input
line, and a send action that walks prompt → client → HTTP transport → response → appends
to scrollback.
**Files:** Create `kernel/src/xk_chat.c3` (app); modify `kernel/src/xk_wm.c3`,
`xk_apps.c3` (register/launch chat window at boot).
**Verification:** Launch QEMU with the mock/TLS-proxy, type a prompt in the chat box, see
the model's reply appear in the window; the client sends the configured
model/endpoint/token.
Commit: `feat(ai): chat box — config + client + WM UI talking to a provider`.

## Stage 2 — Agent territory (later, out of current scope)

Goal: turn the chat client into a supervised agent. Planned (not started until Stage 1 ships):
- `agentd` ring-3 supervisor process (distinct-CR3 pattern from `xk_umode.c3`) owning an
  agent session, calling the LLM through new `int 0x80` agent syscalls
  (`SYS_AI_PROMPT`, `SYS_AI_RESPONSE`).
- **Safe action grammar** — constrain the model to a fixed token grammar
  (open/focus/close/type a window) parsed into structured WM calls; every action written
  to an **audit journal** ("audit by design").
- `ai chat "…"` shell builtin mirroring the chat-box path headlessly.

## Stage 3 — Agent territory (later)
- Self-aware display: serialize the WM scene graph + recent event stream + journal into a
  context pack the model consumes directly, closing the perception/action loop.
- Continuity snapshot to FAT for reboot survival; provider config switching at runtime.

## Validation strategy
- After every task: `./build.sh` then `scripts/boot_verify.sh` (desktop up, shell driven,
  screenshot); keep harness words lowercase.
- Client request/response proven by host-side C3 harnesses asserting exact JSON bytes.
- Networking de-risked incrementally: NIC RX first, then TCP, then HTTP, then a real
  chat-box round-trip — each against a local plaintext mock over a QEMU port-forward.

## Risks, tradeoffs, open questions
- **TLS on HTTPS providers is the hardest real blocker.** OpenAI / OpenCode Go are
  HTTPS-only; hand-rolling TLS from scratch is a large no-borrowed-code project. Stage 0.4
  deliberately resolves this *before* the chat box lands. The shippable demo runs against a
  local plaintext/host-terminated endpoint; public-Internet HTTPS is a tracked milestone.
- **QEMU DMA-to-guest has been flaky before** (the AHCI path) — Stage 0.0 spike catches
  NIC-DMA problems early and cheaply.
- **Credential handling:** token stored plaintext on the FAT image (acceptable for a hobby
  OS); never commit a real token — `mkfat` seeds a placeholder.
- **Provider drift:** OpenAI-compatible `chat/completions` covers OpenAI and most gateways;
  exotic schemas are a parser tweak, not an architecture change.
- **Ring-3 generalization** deferred to Stage 2 (`agentd` may need to coexist with
  `sys_prog.asm`; README's one-process constraint lifted then).
- **Per-task commits** so each stage is independently demonstrable.
